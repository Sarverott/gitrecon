# Scrapnote: why the checks failed, the second circle, the band

## Why the workflows failed

Three different things looked like one:

1. **One test, on the runner's Python.** `test_translate_command` failed with
   `unrecognized arguments: hello world`. The runner's Python is 3.12.3; before 3.12.7
   argparse closes a `nargs="*"` argument as soon as an option follows the subcommand, so
   `translate text --from en --to pl hello world` lost its words. Not a test problem: the
   command itself was broken on such Pythons. The entry point now collects the words
   (`cli._late_positionals`); the suite passes on 3.12.3 too.
2. **One commit message.** "Update issue templates with standard proposed examples" was
   written by GitHub's settings page, is not a Conventional Commit, and failed the message
   check of every pull request carrying it - it would have gone on failing at every stage
   of the loop. That wording is now allowed.
3. **Runs without jobs.** For a pull request the loop opens, GitHub also creates a run for
   the pull-request event; it belongs to the bot and waits for approval or ends with
   "workflow file issue" and no log. The run that counts is the one the loop dispatches. I
   could not read more out of those runs than that - they have no jobs to look at.

## GitGuardian workflow and issue templates

- The workflow as the dashboard gives it works; changed: `actions/checkout` v3 -> v7 (as in
  the other workflows), read-only permissions, and no scan for pull requests from forks
  (they get no secret, so the scan could only fail; their commits are scanned on push).
- Issue templates were GitHub's generic ones (browser, smartphone, an empty "custom"). Now:
  a bug report asking for the command, version, extras and token kind, with a warning not to
  paste secrets; a feature request by area; "Teach gitrecon something" for languages,
  frameworks and import styles (mostly data in `resources/`); and links to the docs and to
  private security reports.

## The second circle

`gitrecon relations FOLDER`: ties between the repositories of one owner, in the order of
how firmly they hold - submodule before dependency; links in code and text moved further out.

- rattish: `rattish` carries `branching-chainer`, `documentation-builder` and
  `ratman-dataedit` as submodules.
- shakespeare: `shakespeare-mobile` depends on `shakespeare-gui` (npm).
- redscope-technologies: no ties inside; one submodule from outside (a wiki).

## The band

`gitrecon score --contributors-band-mode`: an instrument per contributor, busiest first. In
this repository that is a duet - the release bot on guitar (it writes the merges and bumps),
the author on bass. `mit-license` in rattish has 74 contributors in its newest 200 commits:
`timidity data/scores/mit-license-band.mid`.
