## Commitizen in five lines

A commit message is a form: `type(scope): subject`, then an optional body and footer. The
type says what kind of change it is; from the types a release knows which version comes next
and what goes into the changelog. `cz commit` asks the form, `cz check` verifies a message,
`cz bump` cuts the version. The scope takes no spaces. That is all of it.

## Ollama: what is connected, what was found

- The server found is the services container on `localhost:11435`; it had no models. I pulled
  `deepseek-r1:1.5b` (1.1 GB) into it, as the note names a small DeepSeek reasoning model.
- Structured answers work as in the note's examples: a pydantic model in, an instance out.
- **deepseek-r1 thinks whether asked to or not.** `think=False` is ignored by this model; with
  a cap of 300 tokens the thinking used them all and the answer came back empty. The cap is
  now 1500.
- **Speed on this CPU:** about 30 seconds per file.
- **Quality of a 1.8-billion-parameter model is weak.** A plan it wrote for four files:

  ```
  modified  .husky/bos/routines.py        refactor(routines): update
  modified  src/gitrecon/cli/content.py   docs: changed: modified
  added     src/gitrecon/llm/__init__.py  docs(llm): language models through Ollama ...
  ```

  Right shape, poor content: types guessed wrong, subjects that say nothing. The form
  guarantees a valid message, not a true one. A model of 7 billion parameters or more
  (`--model`) is the realistic minimum for messages worth keeping; which one is your choice.
- Asked for the capital of Poland in one word, it said "Gniezno". Historically defensible.

## A commit per file: how it behaves

`gitrecon commit-files` prints a plan and commits nothing. `--apply` makes one commit per
file; the hooks run for each (sync, tests, message check), but the routines that act on the
whole tree are switched off for the series (`BOS_SKIP_ROUTINES=add-all,push`, new in
`.husky/bos/routines.py`) - otherwise the first commit would stage everything and push. It
stops at the first commit a hook refuses. It does not push.

One thing to know: the pre-commit hook stages `package.json`, `pyproject.toml` and the
lockfiles; if those have pending changes they ride along with the first commit of a series.

## Later the same day: two models, measured

`qwen2.5-coder:7b` was pulled, and the reader idea of the note built: `--reader MODEL` lets one
model study a file first (gitrecon's own facts about it - language, lines changed, what it
uses, who uses it - and the diff) and hand notes to the writer. The same nine files of commit
`ac23e3f`, replayed in a scratch clone:

| Setup | Time for 9 files | What came out |
| --- | --- | --- |
| `deepseek-r1:1.5b` alone | about 4.5 min (from 4 files) | right shape, little content: `docs: changed: modified` |
| `qwen2.5-coder:7b` alone | 2 min 50 s | `feat: add BOS_SKIP_ROUTINES environment variable to skip routines` - true and useful |
| deepseek reads, qwen writes | 6 min 16 s | worse: the reader invented things and the writer repeated them |

What the reader got wrong, for the record: of `routines.py` it noted "adds the `add-all`
routine and updates the `push` command to `branch`" (neither happened); of `scrapnote.py`
"reads the script name and language from sys.argv". The writer, working from those notes,
wrote them into the commit message. Alone, reading the diff itself, it described both files
correctly.

So the pipeline of the note is right in form - a reader that gathers everything, then a
writer - but the reader must not be the weaker of the two. A second finding on the way: the
fallback's guess "type: chore" in the prompt talked the writer out of `feat`; without it the
types came out right.

## Decision after the measurements: parked

The Ollama approach is set aside. In the code:

- `src/gitrecon/llm/` - the interface and the model-backed commit handler are commented out;
  nothing imports them; the `gitrecon llm` command is gone; their tests are skipped.
- the per-file committing was taken apart from the model and is now `gitrecon.committing`:
  what changed and in which order, the commit form, a registry of **handlers**, the plan.
  A handler is a function that answers the form for one file; only the plain `path` handler
  exists. Whatever comes next is written as a handler.

The models pulled into the Ollama container are still there (`deepseek-r1:1.5b`,
`qwen2.5-coder:7b`): removing them is `docker exec gitrecon-ollama-1 ollama rm NAME`.
