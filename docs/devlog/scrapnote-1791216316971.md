## OpenSpec in six lines

- A **spec** says what a capability must do: requirements, each with scenarios (WHEN / THEN).
  Specs live in `openspec/specs/<capability>/spec.md` and describe the system *as it is*.
- A **change** is a folder in `openspec/changes/<name>/` with four files: `proposal.md` (why,
  what), `specs/` (the requirements it adds, modifies or removes - a *delta*), `design.md`
  (decisions), `tasks.md` (a checklist).
- The loop of one change: **propose** -> review the four files -> **apply** (an agent works
  the tasks) -> **archive** (the delta is merged into the main specs; the folder moves to
  `changes/archive/`).
- So the question "what did we decide and what must still hold" stops living in chat
  history and scrapnotes: it lives in files that are validated (`openspec validate`).
- It does not replace tests, docs or the branch loop. It sits *before* the code.
- Useful commands: `openspec list`, `openspec list --specs`, `openspec show NAME`,
  `openspec status --change NAME`, `openspec validate --all --strict`, `openspec view`.

## Things that will bite, found while checking

1. **Only Copilot got the OpenSpec tooling.** Any other agent (this one included) has no
   `/opsx-*` commands here. `openspec init --tools github-copilot,claude` (or `agents` for a
   plain AGENTS.md-based setup) adds them; the CLI itself works for everyone already.
2. **The Copilot cloud agent cannot run this project's checks yet.**
   `copilot-setup-steps.yml` installs only the OpenSpec CLI - no uv, no Task, no test
   dependencies. It also uses `actions/checkout@v4` where the other workflows use v7. The
   file is generated ("Generated by OpenSpec"), so `openspec update` may overwrite edits:
   keep additions small and re-check after an update.
3. **The loop does not know Copilot's branches.** `bos-flow.yml` opens pull requests for
   `feature/**` and `fix/**`; the cloud agent pushes to `copilot/*`. Its pull requests into
   `development` will get the PR checks only if opened by a person or added to the loop.
4. **Commit messages.** Every commit of a pull request is checked (`cz check`). An agent that
   writes "Initial plan" or "Update file" blocks the loop the same way the browser commit
   did. The rule is in `config.yaml` now; it is also worth one line in the Copilot
   instructions.
5. **`CLAUDE.md` lost its final newline** in the GitNexus clean-up. Harmless; one keystroke.
6. Untracked files in the repository root that look like leftovers: `testdisk.log`, `site/`.

## The steps, in order

1. Read `openspec/changes/baseline-per-file-commits/` - mainly `specs/per-file-commits/spec.md`.
   This is what a spec of *your* code looks like. Correct anything that is not what you want
   the tool to promise.
2. Decide the agent question (point 1 above): Copilot only, or also others.
3. Commit the OpenSpec files (`openspec/`, `.github/agents`, `.github/prompts`,
   `.github/skills`, the workflow) - as `chore(openspec): ...` or `build(openspec): ...`.
4. Archive the baseline: `openspec archive baseline-per-file-commits`. From then on
   `openspec list --specs` shows one capability.
5. Run the first *real* change through it end to end - the next commit handler is the
   natural one: propose -> review -> apply -> archive. One full pass teaches more than any
   amount of preparation.
6. After that pass, decide what to trim: the rules in `AGENTS.md` that now live in
   `config.yaml`, and whether scrapnotes keep their "Open" lists.
7. Bring in further capabilities only when a change touches them.
