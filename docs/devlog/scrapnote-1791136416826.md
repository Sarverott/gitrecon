## Answers (added by Cleo, 2026-10-04)

**1. "forbids access via a personal access token (classic)" - do we block something?**
Yes, and on purpose: the organization The-Apokryf has *Settings → Personal access tokens →
restrict access via personal access tokens (classic)* switched on. Classic tokens (`ghp_...`)
are all-or-nothing keys over everything their owner can reach, so the organization refuses
them through the API - even for its public data, when the request carries such a token. The
token gitrecon uses (the forge `.env` and the `gh` login hold the same one) is a classic one.

**2. "GraphQL answered partly (N refused)" - what is in there?**
Each refused item is one fork whose **upstream lives in The-Apokryf**. For Sarverott's own
forks, the six are: `csharpest`, `rattlesnake-ultimate`, `The-Apokryf.github.io`,
`web.sms.ngo`, `omnilibris`, `webdev-omnitoolkit`. GraphQL returns the fork but hides its
`parent`, because naming it would touch that organization. REST still names the parent when
asked about the fork itself (`GET /repos/Sarverott/csharpest` → `The-Apokryf/csharpest`), so
gitrecon now asks REST for exactly those and the edges are back: `Sarverott → The-Apokryf: 6`.
The single refusals in other organizations are the same thing: one fork each of a
The-Apokryf repository.

**3. "use a GitHub App, OAuth App, or a fine-grained token" - a particular one, or any?**
Any of the three kinds, but it has to be *authorized for The-Apokryf* - the name of the app
does not matter, its relation to the organization does:

- a **fine-grained token** whose *resource owner* is The-Apokryf (one such token covers one
  owner; the organization can require approving it) - read-only "Metadata" and "Contents"
  are enough for gitrecon;
- an **OAuth App** token - e.g. `gh auth login --web` logs the GitHub CLI in through OAuth
  (`gho_...`) instead of a pasted classic token; if the organization restricts third-party
  apps, "GitHub CLI" needs approving once in its settings;
- a **GitHub App** installed on The-Apokryf (its installation token).

What is still not seen: the upstreams of The-Apokryf's own 98 forks (the summary lists it
under "not seen"). Its public repositories themselves are listed - without the token.

What changed in gitrecon after this note:

- one warning per organization instead of one per page;
- "answered partly" is no longer a warning (the gaps are filled through REST);
- `gitrecon network` ends its summary with "not seen:" when something stayed hidden.

Next step worth taking: **a token per owner** - e.g. `GITHUB_TOKEN__THE_APOKRYF` holding a
fine-grained read-only token for that organization, used only for requests about it, while
everything else keeps the general token.
