## PeekerLex and CaptorLex

tree-sitter does not *understand* code. It gives a complete syntax tree: this is a function
named X with these parameters, it calls Y, it is inside class Z. That is structure - the
first step of CaptorLex, not all of it:

| | PeekerLex | CaptorLex 1: structure | CaptorLex 2: relations | CaptorLex 3: meaning |
| --- | --- | --- | --- | --- |
| knows | comment, string, name, number | function, class, import, call | who uses whom, across files and repositories | what it is for, why it is so |
| tool | Lark lexers, tables | `ast` (Python), tree-sitter (others) | a graph over step 1 (networkx is in core) | language models over steps 1-2 |
| speed | hundreds of files a second | tens of files a second | minutes per owner | seconds per function |
| state | built | Python only | not built | not built |

## Humanish: the question, expanded

What exists in `gitrecon.text`: a tokenizer that turns text into *word chains* per sentence,
and the a12y glossary that gives every word a short key. So a sentence is already a sequence
of known tokens - the same thing a lexer gives for code. A lexer is where a grammar starts.

The question was: is there a description of which *shapes* of sentences humanish has? A
grammar needs that. Three levels, from sure to ambitious:

1. **Controlled sentences** - text that already follows rules. Commit messages
   (`type(scope): subject`), changelog lines, RFC keywords (MUST, SHOULD, MAY - RFC 2119),
   licence clauses. A grammar here is small, exact and useful to gitrecon now: labels and
   digests could be concluded from parsed commits rather than regex guesses.
2. **Normative text** - documentation, statutes, constitutions. The shape is regular: *who*
   (subject) + *modality* (must, may, must not) + *action* + *condition* (if, unless, within
   N days) + *reference* (art. 5 ust. 2). Polish legal text is unusually regular in its
   skeleton - artykuł, ustęp, punkt, litera, cross-references - so the **skeleton** parses
   with a plain grammar, and each provision becomes a record: who, modality, what, when,
   refers to. That is what a model needs to reason about law without inventing it: the
   grammar says what the text *says*, the model explains it.
3. **Free text** - no grammar covers it; a model reads it, and the grammars of levels 1-2
   check the model's output shape.

Where that touches the two projects named: Polish law parsing is level 2 almost exactly (a
grammar of the act's skeleton + a grammar of the provision's sentence). For necropools I do
not know the project - what its texts are decides the level.

Both are separate projects; what gitrecon would share with them is only the method: tokens ->
grammar in `resources/` -> records.

**So the question, concretely:** should gitrecon get level 1 now (a grammar for commit
messages and for RFC 2119 keywords, feeding labels), as the small first proof of the method?

## The git graph as a score

A gitGraph already has what a score has: lanes are strings (or voices), commits are notes in
time order, a merge is two voices meeting, a tag is a bar line. A mapping that needs no
decisions from a musician: lane -> pitch (master lowest), time between commits -> duration,
merge -> chord of both lanes, revert -> rest. Output as MIDI or ABC notation is a small
function over the same commit list `gitgraph --json` prints.
